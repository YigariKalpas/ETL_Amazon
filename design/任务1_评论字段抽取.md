# 任务1 评论字段抽取（已完成）

> 依据：作业 §五 任务1「从原始评论数据中抽取评论字段」。
> 源文件：movies.txt/movies.txt，8.69 GB；全程**流式逐行**，未把原文读入内存或上下文。
> 产出位置：data/staging/reviews/。

## 一、原始格式（实测，非假设）

用 crawler/probe_review_format.py 扫前 20 万行确认，每条记录 8 个字段 + 空行分隔：

| 字段 | 含义 | 实测长度 |
|---|---|---|
| product/productId | ASIN，10 位大写字母数字 | 10 |
| review/userId | 评论者 ID | 12–14 |
| review/profileName | 昵称（可能带引号别名） | 2–48 |
| review/helpfulness | 有用票 n/m | 3–7 |
| review/score | 1.0–5.0 | 3 |
| review/time | Unix epoch（秒） | 10 |
| review/summary | 标题 | 3–87 |
| review/text | 正文 | 63–4858（全量最长 34,715） |

## 二、产出文件

| 文件 | 内容 |
|---|---|
| part-00001.csv.gz … part-00040.csv.gz | 主数据，每片 20 万条，gzip CSV，共 3,212.5 MB |
| product_review_counts.csv | 253,059 行，每个产品的评论条数 |
| rejects.csv | 74 条异常记录明细（不静默丢弃） |
| stats.json | 总量、异常计数、评分分布、时间范围、文本长度 |
| manifest.json | 40 个分片的 SHA-256 清单 + digest_of_parts |

主数据 13 列：

| 列 | 说明 |
|---|---|
| asin | 产品 ASIN（已校验 ^[A-Z0-9]{10}$） |
| user_id / profile_name | 评论者 |
| helpful_num / helpful_den | 有用票分子分母，解析失败留空并计数 |
| score | 1.0–5.0，越界置空并计数 |
| review_time_epoch / review_time_iso | 原始 epoch 与 UTC ISO8601 双列 |
| summary / text | 原文（去掉键后的一个空格） |
| summary_len / text_len | 字符数，便于后续过滤 |
| record_index | 源文件中的第几条记录，供字段级血缘回溯 |

### 人工逐条核对（抽查 3 条）

    .venv\Scripts\python.exe crawler\verify_reviews.py --sample 3

对照源文件同一 ASIN 的记录（例如先查 product_review_counts.csv 拿到条数，再解压对应分片数行）。

### 与源文件对照的最短路径

1. 从 product_review_counts.csv 选一个 ASIN，例如 B002QZ1RS6（957 条）；
2. 在 part-*.csv.gz 中检索该 ASIN（脚本已能扫）；
3. 条数应与 count 列一致 — 这是端到端的一致性校验。

## 六、设计要点与踩坑（写进报告可加分的部分）

| 项 | 说明 |
|---|---|
| 流式解析 | 8.69 GB 只用常量内存；块解析（空行提交）避免半条记录入库 |
| 分片轮转 bug | 第一版 close_part() 没把计数归零，导致第 2 个分片写入时 writer 为 None → AttributeError，跑到 200k 条就崩。修复后 40 片正常 |
| 中断的残留 | 进程被杀会留下 0 字节的半截 part 与过期 stats.json。判定方法：python 进程是否为 0 + stats.json 时间戳早于最新 part + 最新 part 大小为 0。恢复方式：删除输出目录重跑（幂等） |
| 异常留痕 | 拒绝记录必须落盘，否则「总量对不上」时无法解释 |
