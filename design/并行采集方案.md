# 多脚本（多进程）并行采集

> 入口：crawler/parallel_crawl.py　worker：crawler/crawl_product_pages.py　自检：crawler/verify_parallel.py

## 一、先说结论：并发不是加速器

实测（Stage 0 全部波次）该出口按**请求预算**限流：每窗口约 130–190 次请求，之后近 100% 验证页。
因此并行**不能提高总请求预算**，只能：

1. 重叠网络等待与落盘 IO，让单次请求的等待时间不浪费；
2. 多进程分担解析与压缩开销；
3. 让抓取更稳定地贴着预算上限跑，而不是单线程串行时的空闲。

所以并行实现的第一原则是：**聚合速率恒定**。每个 worker 的请求间隔 = 全局间隔 × worker 数，
总速率始终等于 1 / 全局间隔（默认 1 请求 / 3 秒），不会因为加 worker 而突发。

## 二、架构

    product_urls.txt (253,059)
            |
            v
    剔除状态库已有 ASIN -> 按 seed 随机抽样 N*W 个
            |
            v
    切成 W 个分片 shard_01.csv … shard_WW.csv（互不重叠）
            |
            +--> worker 1（独立进程，delay = 全局间隔 × W）
            +--> worker 2
            +--> worker W
                   |
                   +--> 共享 SQLite（WAL + busy_timeout=15s）
                   +--> 共享 data/raw/pages/<sha1[:2]>/（按 ASIN 分桶，不冲突）
                   +--> 共享 data/crawler/PAUSE（跨进程退避信号）

## 三、关键实现

| 机制 | 做法 | 解决什么 |
|---|---|---|
| 分片不重叠 | 主控先抽样再均分，worker 只读自己的 shard，不接受 --sample | 重复抓同一 ASIN |
| 聚合限速 | 每 worker 间隔 = 全局间隔 × workers | 加 worker 后请求突发 |
| 跨进程退避 | 任一 worker 判定被限流 → 写 PAUSE（截止 epoch）→ 所有 worker 在 wait() 里等待 | 各撞各的验证页、越撞越狠 |
| SQLite 并发 | PRAGMA journal_mode=WAL + busy_timeout=15000 | database is locked |
| 原子状态写入 | 原有 UPSERT + 主键 | 重复行 / 覆盖 |
| 统一停止 | 主控监控 STOP、磁盘水位、max-hours，超限时 terminate 全部 worker | 失控长跑 |

## 五、运行方式

    # 3 个 worker，每个 200 个目标，聚合 1 请求 / 3 秒
    .venv\Scripts\python.exe crawler\parallel_crawl.py --workers 3 --per-worker 200 --global-interval 3 --max-hours 4

    # 只看分片怎么切，不发请求
    .venv\Scripts\python.exe crawler\parallel_crawl.py --workers 4 --per-worker 50 --dry-run

    # 停止：写 STOP，主控会 terminate 所有 worker
    New-Item data\crawler\STOP -ItemType File -Force

    # 分片自检（互不重叠、全部入库）
    .venv\Scripts\python.exe crawler\verify_parallel.py

## 六、参数建议

| 参数 | 建议 | 理由 |
|---|---|---|
| workers | **2**（默认） | 实测 3 worker × 3 s 时约 260 次请求就把预算打光，验证页占 54%；2 个足够重叠等待 |
| global-interval | **6–8 s**（默认 6） | 预算约 130–190 次/窗口，6–8 s 可让预算撑 15–20 分钟而不是 10 分钟 |
| per-worker | 100 | 与预算窗口匹配 |
| max-hours | 4 | 超过就停，避免休眠空转占用运行时长 |
| purge-every-min | 30 | 清理验证页快照并回填待采集（并行模式不会自动清，必须定时做） |
| refresh-every-min | 0 | 采集中刷新代价高，默认只在结束时刷新一次 |
| no-refresh-at-end | 关 | 结束自动跑一次 run_pipeline.py，把新增页面写进目标层 |
| initial-cooldown-min | 20（被限流后） | 刚撞过验证页立刻重启会继续吃验证页，先等一段时间再开工 |

## 六点五、维护自动化（脚本内建）

并行采集期间有两件维护必须定时做，否则数据会"采到但没落库"：

| 维护 | 触发 | 命令 | 输出 |
|---|---|---|---|
| 清验证页 | 每 30 分钟 | purge_invalid_snapshots.py --apply | logs/purge.log |
| 刷新目标层 | 采集结束后（默认） | run_pipeline.py | logs/refresh.log |

主控在监控循环里按时间差触发，不需要额外的计划任务。想中途也刷新，加 `--refresh-every-min 60`。

## 七、持续采集策略（当前运行）

目标：在站点允许的范围内尽量多采，但不在验证页上浪费预算。

    .venv\Scripts\python.exe -u crawler\wave_loop.py --delay 14 --delay-max 30 --jitter 2 --concurrency 2 --sample-per-wave 100 --target-success 5000 --max-hours 12 --cooldown-ok 240 --cooldown-blocked 3600 --cooldown-cap 14400 --blocked-if-gain-lt 30 --max-blocked-waves 6 --abort-after-blocks 2 --refresh-every-waves 5

| 参数 | 值 | 理由 |
|---|---|---|
| 单 worker（并发 2 线程） | — | 健康窗口实测 79%–87%，并行不提升总产出 |
| delay | 14 s | 历史健康波最稳的节奏 |
| abort-after-blocks | 2 | 连续 2 轮窗口恶化就停，避免 wave_010 那种 19% 的浪费 |
| cooldown-blocked | 3600 s 起，封顶 14400 s | 重度突发后 20–30 分钟不够，按小时等 |
| refresh-every-waves | 5 | 每 5 波刷新一次目标层，控制落库滞后 |
| max-hours | 12 | 单次运行上限，到点自动退出 |
| target-success | 5000 | 与作业可交付样本量匹配，不追求 25 万全量 |

## 八、已知边界

1. 并行不会突破站点预算，遇到限流仍会集体暂停，总产出与「单线程 + 同等聚合速率」基本一致；
2. 每个 worker 单独重试与超时，某 worker 卡在慢页面时其他 worker 不受影响（这是并行的真实收益）；
3. 状态库是唯一并发写点，已用 WAL 缓解，但 worker 数不建议超过 4；
4. 分片是一次性的：重跑会重新抽样，旧分片文件保留在 data/crawler/shards/ 供核对。
