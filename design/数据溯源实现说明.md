# 数据溯源（字段级血缘）实现说明

> 对应作业 §九：回答「某部电影的某个字段是什么、从哪些原始记录抽取、经哪些清洗/匹配/推断形成、最终为何采用这个值」。
> 演示脚本：crawler/trace_evidence.py（实测 PASS）；生成脚本：crawler/build_field_assertions.py。

## 一、四段证据链

    L1 原始证据      source_record（页面：URL/快照路径/SHA-256/抓取时间）
                     source_file  （评论：分片文件名/行数/SHA-256）
         |
         v
    L2 抽取断言      field_assertion（entity+field+raw_value+locator+rule_id+run_id+confidence）
         |
         v
    L3 集成决策      merge_decision（合并候选与证据：标题相似度/导演/演员/片长/规则号）
                     product_movie（商品到作品的归属关系与类型）
         |
         v
    L4 最终选择      field_selection（selected_assertion_id、候选数、理由、状态）

关键点：每一段都有落盘的表，且段与段之间用 ID 相连，不依赖日志或口头说明。

## 二、两张核心表

### field_assertion（候选值）

| 列 | 作用 |
|---|---|
| assertion_id | 断言主键（如 FA-<asin>-<field> 或 FA-<review_id>-text） |
| entity_type / entity_id | movie / product / review 及其 ID |
| field_name / raw_value / normalized_value | 哪个字段、原始值、规范化值 |
| source_record_id | 指向 source_record（页面断言）或商品 ASIN（评论断言） |
| locator | 精确定位符，格式见第三节 |
| rule_id | 哪条抽取规则产生（parse_product_page/v1、extract_reviews/v1、movie_entities/v1） |
| run_id / confidence / created_at | 批次、置信度、生成时间 |

### field_selection（最终选择）

| 列 | 作用 |
|---|---|
| entity_type / entity_id / field_name | 定位字段 |
| selected_assertion_id | 最终采用的断言（空表示缺失） |
| candidates | 候选数量 |
| reason | 选择理由（唯一候选 / 仅有评论上界 / 页面日期属商品发售日 等） |
| status | selected / inferred_only / missing / conflict |

## 三、定位符规范

| 实体 | locator 格式 | 示例 |
|---|---|---|
| product / movie 字段 | 快照 SHA-256 加 JSON 路径 | 3aab5fcf...18a2#$.title_raw |
| review 字段 | 分片文件名加记录号 | part-00001.csv.gz#record=8 |

页面类断言用内容哈希而不是文件名定位：即使文件改名或换目录，只要内容不变仍能命中。
评论类断言用分片加记录号，与 extract_reviews 写入时的 record_index 一一对应。

## 四、生成链路（谁在哪一步写什么）

| 步骤 | 脚本 | 写入 | rule_id |
|---|---|---|---|
| 采集 | crawl_product_pages.py | source_record：snapshot_path / content_sha256 / fetched_at | — |
| 评论抽取 | extract_reviews.py | source_file（分片 SHA-256）；每行带 record_index | extract_reviews/v1 |
| 页面解析 | parse_product_page.py | 暂存 JSON 记录 snapshot_sha256 | parse_product_page/v1 |
| 断言生成 | build_field_assertions.py | field_assertion（product / movie / review 三类） | 三种前缀见上 |
| 实体合并 | movie_entities.py | merge_decision（证据、规则号、置信度） | movie_entities/v1 |
| 冲突选择 | field_conflicts.py | field_selection 与 conflicts.csv | field_conflicts/v1 |
| 落盘 | build_target_db.py、load_target_pg.py | 上述表进 SQLite 与 PostgreSQL | — |

## 五、端到端实测（trace_evidence.py 输出）

### A. 页面字段

    assertion_id   = FA-E-0159505100-canonical_title
    entity         = movie/E-0159505100  field=canonical_title  value=Out of the Tombs [VHS]
    source_record  = 0159505100
    locator        = 3aab5fcf...18a2#$.title_raw
    rule_id        = movie_entities/v1  confidence=0.8
    snapshot_path  = data/raw/pages/54/0159505100.html.gz
    fetched_at     = 2026-10-27T04:13:06Z
    sha256(库)     = 3aab5fcf...18a2
    sha256(重算)   = 3aab5fcf...18a2
    PASS  三处哈希一致（库登记、磁盘重算、locator 前缀）

### B. 评论字段

    assertion_id = FA-RV-54fe7d9b90e898d1-text
    review_id    = RV-54fe7d9b90e898d1
    raw_value    = sha256:db5e8f2d...c044;len=1709
    locator      = part-00001.csv.gz#record=8
    asin=B00006HAXW user=AD4CDZK7D31XP score=5.0 time=2003-08-10T00:00:00Z
    sha256(重算) = db5e8f2d...c044
    PASS  断言摘要与重读分片计算的一致

两步都是现场重算：页面重算 SHA-256、评论重读分片再算一次文本摘要。

## 六、自己复核的方式

    # 一键跑两条链路并当场比对哈希
    .venv\Scripts\python.exe crawler\trace_evidence.py

    # 查某个电影的所有断言
    .venv\Scripts\python.exe crawler\db_query.py SELECT field_name,raw_value,locator,rule_id FROM field_assertion WHERE entity_type='movie' AND entity_id='E-0159505100' --db data\target\target.db

    # 查字段选择理由
    .venv\Scripts\python.exe crawler\db_query.py SELECT field_name,status,reason FROM field_selection WHERE entity_id='E-0159505100' --db data\target\target.db

## 七、边界与取舍

| 项 | 处理 | 原因 |
|---|---|---|
| 评论正文过长 | raw_value 存 sha256 加长度，原文用 review_id 回查 review 表 | 避免血缘表被全文撑爆，同时保留可校验性 |
| release_year 无可信来源 | 不生成断言，field_selection 记 missing / inferred_only | 作业要求查不到保留缺失，不得编造 |
| 推断值（最早评论上界） | 单独 status=inferred 与 condition 说明 | 推断不得覆盖已核实日期 |
| 合并候选未通过 | merge_decision 保留 reject 与理由 | 支持检查与纠正误合并 |
| 外部数据缺失 | 任务6 verified=0，明确写进报告 | 不把 inferred 冒充 verified |
