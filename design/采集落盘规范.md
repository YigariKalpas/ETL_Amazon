# 采集数据落盘规范（任务2 / 原始层与暂存层）

> 目标：把爬虫产出的「原始证据 + 抽取结果 + 采集状态」按作业 §八 的分层组织，
> 保证可追溯、可复现、可增量、且不把大文件塞进 Git。

## 一、分层与职责（对齐作业 §八）

| 层 | 内容 | 谁产生 | 是否可变 |
|---|---|---|---|
| **原始层** | 产品页原始响应（gzip）、第三方数据原文 | 爬虫 | **不可变**（只追加，不覆盖） |
| **暂存层** | 从快照抽取的结构化字段 JSON | `parse_product_page.py` | 可重算（可按 `rule_version` 全量重建） |
| **集成层** | 电影/人物归并、字段断言与选择 | 后续（PDI + Python） | 可重算 |
| **目标层** | PostgreSQL 中的实体、关系、血缘 | PDI 装载 | 幂等 upsert |

关键原则：**原始层永远是唯一事实来源**；暂存层与集成层都可以由原始层重新计算。

## 二、目录结构（建议）

```
data/
  raw/
    pages/<bucket>/<ASIN>.html.gz      # 原始响应，不可变
    third_party/                       # IMDb / 豆瓣等（若使用）
  crawler/
    product_list.csv                   # 253,059 个 ASIN 清单
    products.sqlite                    # 采集状态机（可重建的索引，非权威数据）
    robots_amazon.txt                  # 合规证据
  staging/
    product_pages/<bucket>/<ASIN>.json # 抽取结果（每 ASIN 一文件）
  manifest/
    collect_manifest.json              # 清单哈希、统计、重跑命令
    run_stats.jsonl                    # 每次运行的统计（追加）
```

**分桶规则（重要）**：`bucket = sha1(ASIN)[:2]`（256 个桶）。
不要直接用 ASIN 前两位——Amazon ASIN 绝大多数以 `B0` 开头，会退化成一个目录装 20 万文件，
在 NTFS 上导致 `Get-ChildItem` 与备份极慢。

## 三、命名与幂等

| 规则 | 说明 |
|---|---|
| 主键 | `ASIN`（10 位） |
| 快照名 | `<ASIN>.html.gz` |
| 抽取结果名 | `<ASIN>.json` |
| 覆盖策略 | 快照**不覆盖**：同 ASIN 再次采集写入带时间戳的新文件或比对哈希后跳过 |
| 幂等键 | 内容 `sha256`（同一页面重复抓取应得到相同哈希） |
| 重建 | 删除 `staging/` 即可，由 `raw/` 重算 |

## 四、容量估算（实测数据推导）

实测单页快照（gzip）：**298.7 KB / 251.9 KB**（正常商品页），**1.1 KB**（404 页）。

| 项 | 计算 | 估算 |
|---|---|---|
| 全量快照（253,059 页 × ~275 KB） | 253059 × 275 KB | **≈ 68 GB** |
| 若只采电影类（假设 2.5–5 万） | 25k–50k × 275 KB | ≈ 7–14 GB |
| 状态库 SQLite（253k 行） | ~300 B/行 + 索引 | ≈ 80–120 MB |
| 清单 CSV | 实测 | 14 MB |
| 暂存 JSON（~1.5 KB/ASIN） | 253k × 1.5 KB | ≈ 380 MB |

**结论**：
1. 全量快照约 **68 GB**，磁盘（当前可用 ~365 GB）可承受，但**绝不能进 Git**；
2. 建议**只对判定为电影/待确认的商品保留完整快照**，其余仅保留状态与哈希；
3. 快照必须 gzip（实测压缩后约为原始 HTML 的 1/4）；
4. 若后续要长期保存，可再转 `zstd` 或按批次归档（tar.zst），但需保留逐文件哈希以便抽查。

## 五、入库（Git）策略

| 类别 | 示例 | 是否入库 |
|---|---|---|
| 脚本与规范 | `crawler/*.py`、`design/*.md` | ✅ 入库 |
| 清单与校验 | `manifest/collect_manifest.json`（含 CSV 的 sha256） | ✅ 入库（小） |
| 抽样证据 | 10–20 个 `<ASIN>.html.gz` + 对应 JSON（覆盖成功/404/验证页/模板异常） | ✅ 入库（< 5 MB） |
| 全量快照 | `data/raw/pages/**` | ❌ 不入库 |
| 状态库 | `products.sqlite` | ❌ 不入库（可重建） |
| 全量清单 CSV | 14 MB | ⚠️ 不入库，但 manifest 记录 sha256 与重跑命令 |

这正好对应作业 §十一 的措辞：**「完整数据较大时提交校验值、保存位置与恢复方法」**。

## 六、恢复与复现（写入报告用）

```cmd
rem 1) 重建 ASIN 清单（约 48 s，9.3 GB 流式）
.venv\Scripts\python.exe crawler\extract_asins.py

rem 2) 续跑采集（终态跳过，只补未完成/可重试项）
.venv\Scripts\python.exe crawler\crawl_product_pages.py --concurrency 2 --delay 3

rem 3) 从快照重建暂存层
.venv\Scripts\python.exe crawler\parse_product_page.py
```

校验方法：`manifest/collect_manifest.json` 内记录 `product_list.csv` 的 sha256；
任意快照可用 `sha256` 与状态库 `content_sha256` 比对，确认未被篡改。

## 七、与目标层的衔接

| 原始/暂存产物 | 目标层表（作业 §八） |
|---|---|
| `products.sqlite` 一行 | `SourceRecord`（源 URL、快照哈希、获取时间）+ `ProductEdition`（ASIN） |
| `<ASIN>.json` 的每个字段 | `FieldAssertion`（raw_value / normalized_value / rule_version / confidence） |
| 快照文件 | `SourceRecord.snapshot_path` |
| `product_list.csv` 的 `first_line` | 评论 → 商品的原始定位证据 |
