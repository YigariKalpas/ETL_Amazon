# 效率复盘、进度对比与人工复查

> 配套主报告：docs/主报告.md；本文回答三件事：
> 1) 这次任务里效率是怎么提上去的；2) 遇到的问题根因是什么；3) 按作业要求怎么做人工复查。
> 所有数字均来自仓库内脚本，复查命令见第四节。

## 一、效率提升的方式与量化效果

| # | 手段 | 问题 | 做法 | 量化效果 |
|---|---|---|---|---|
| 1 | 全流程脚本化 | 8.69 GB 原文、7.9 万级记录不可能进对话上下文 | 流式逐行解析 + 分片落盘，只读产物 | 7,911,684 条评论 992 秒完成；内存恒定 |
| 2 | 快照本地化 + 哈希 | 重复抓取会浪费本就稀缺的请求预算 | gzip 快照 + SHA-256 登记，离线重放 | 2,623 个快照零缺失零孤儿（landing_compare） |
| 3 | 分桶存储 | 单目录放 25 万文件不可行 | sha1(ASIN)[:2] 分 256 桶 | 2,624 文件分散在 256 桶，读写正常 |
| 4 | 自适应退避 | 被限流后继续请求只是烧预算 | 滑动窗口判定 + 指数暂停 + 波间冷却 | 健康波成功率 73%-87%，受限波在 2-3 轮内中止 |
| 5 | 跨进程共享暂停 | 并行 worker 各自撞墙 | PAUSE 文件共享截止时间 | 3 worker 实测无验证页风暴，SQLite 无 database is locked |
| 6 | 中止真正生效 | 中止后已提交的 future 仍在抓 | abort_event + cancel_futures | 每次中止少发约 190 次无效请求 |
| 7 | 幂等装载 | 重跑会产生重复实体 | INSERT OR REPLACE + 主键 | 连跑两次 17 张表行数与摘要完全一致 |
| 8 | 关闭 PG 并行查询 | 简单 COUNT 卡 10 分钟 | max_parallel_workers_per_gather=0 | 19 张表装载由挂起变为数分钟内完成 |
| 9 | ETL 定时调度 | 人工跑管线频率不稳定 | 每 4 小时自动执行 PDI 作业 | 单轮 8 分 46 秒、rc=0，历史落 schedule_history.csv |
| 10 | 逐层比对 | 采集与落盘差多少靠猜 | L0→L4 五层对账 | 滞后从 373 条降到 26 条可量化 |
| 11 | 开波前窗口探测 | 被限流时整波 100 次请求可能全废 | crawler --probe 先发 1 个请求，被限流直接跳过整波 | 每波省 20-30 次无效请求；被限流时不消耗波次 |
| 12 | 空闲快速跳过 | 无新数据时 ETL 仍全量重跑（约 9 分钟） | run_pipeline 按采集库指纹判断，无变化直接返回 | 实测无变化时 0.3 秒返回（从 500 秒降到 0.3 秒） |
| 13 | PG 装载非阻断 | PG 挂掉导致整轮 ETL rc=1 | 11_load_pg 失败跳 WARN 节点再继续 verify | 失败桩实测：流程仍到 Success，退出码 0 |
| 14 | 自适应波次 | 受限时硬跑 100 个把预算喂给验证页 | 上波成功率 <40% 缩到 60%，>70% 放大到 100 | 受限波不再整波空烧 |
| 15 | 实体匹配分块 | movie_entities 全量两两 difflib，3.2k 商品要 40+ 分钟 | 按标题 token 建倒排索引，只比同桶候选 | **45 分钟 → 34.5 秒**（候选对 530 万 → 5 万，实际比较 87 对） |

## 二、问题根因分析（按来源分类）

### 2.1 运行环境（沙箱/Windows）

| 问题 | 根因 | 影响 | 处置 |
|---|---|---|---|
| pip 安装 PermissionError | 沙箱下 os.mkdir(0o700) 产生的 DACL 不含受限 SID | 装不了依赖 | sitecustomize.py 在 win32 把 mode 放宽为 0o777 |
| PowerShell 语言模式受限 | ConstrainedLanguage 禁用 .NET 静态调用 | 脚本写法受限 | 关键逻辑改 Python，.ps1 只做薄封装 |
| tasklist 被拒 | 受限令牌无权限 | 无法直接列进程 | 各守护进程写 runtime 标记 + 日志心跳 |
| 临时目录消失 | DSH 临时目录被回收 | 命令直接失败 | 重建目录 + 关键产物全部落工作区 |
| pg_ctl 不可用 | 无法创建受限令牌（error 87） | 启停脚本失效 | 直接运行 postgres.exe 由后台任务托管 |
| 并行 gather worker 起不来 | 同源（进程创建受沙箱限制） | COUNT/COPY 假死 | 服务端与客户端都关 max_parallel_workers_per_gather |
| .cmd 必须纯 ASCII | cmd.exe 按 GBK 解析 | 中文路径直接崩 | 中文规则文件复制为 ASCII 名，注释全英文 |

### 2.2 数据源（站点限流）

- **现象**：间隔 3 秒时约 133 次请求后即近 100% 验证页；10 秒时约 190 次；
- **根因**：站点按**请求预算**限流（时间窗口内的请求数），不是按瞬时 QPS；并发不能提高预算；
- **影响**：全量 253,059 页在限流下需 1,200 小时以上，只能做抽样；
- **处置**：14-18 秒节奏 + 自适应暂停 + 波间冷却 30-240 分钟；并行采集仅用于重叠等待，不追求提速。

### 2.3 数据层（并发与恢复）

| 问题 | 根因 | 处置 |
|---|---|---|
| database is locked | 多进程写同一 SQLite | WAL + busy_timeout=15s |
| PG 集群卡在 starting up | 进程被强杀后恢复不完整 | 重建集群 + 重载（数据来自 SQLite，可重建） |
| COPY 无限等锁 | 中断的 COPY 留下事务锁 | 装载前 terminate 残留后端 + lock_timeout=15s |
| COUNT 假死 | 并行 worker 起不来 | 关闭并行 gather（见 2.1） |

### 2.4 代码缺陷（已修复，都是实测发现）

| 缺陷 | 症状 | 修复 | 证据 |
|---|---|---|---|
| chunk 一次性提交 200 个 future | 中止后仍继续发请求 | 中止事件 + cancel_futures | 修复前中止仍发约 190 次 |
| 连续计数退避 | 限流期夹一次成功就清零，退避永不触发 | 改为滑动窗口（10 次中 4 次即暂停） | wave_010 只有 19% 成功率 |
| 管线步骤顺序 | release/conflicts 读到旧库（967 vs 1,242 个 movie） | 先落盘再算上映/冲突，最后再落盘 | pipeline_run4 前后 movie 数不一致 |
| 控制台编码 | 子进程输出含替换字符导致 UnicodeEncodeError | stdout/stderr 强制 UTF-8 | 管线曾中途崩溃 |
| 检查脚本读错库 | db_query 默认连采集库，查目标表报 no such table | 显式 --db 指向 target.db | 排查过程记录 |

### 2.5 数据源缺口（非缺陷，属客观限制）

- 任务6 上映年份需要 IMDb/豆瓣导出文件，当前 `verified = 0`；
- 人物缺外部 ID，跨语言与音译合并无法做；
- 这两项在报告里如实标注，不用推断值冒充。

### 4.4 复查发现问题的处置顺序

1. 若是**数据缺失**（快照/分片）：先看 landing_compare 的缺失清单，重采或重跑解析；
2. 若是**口径分歧**（分类/合并）：回到 design/产品分类口径_裁定.md 与任务4文档，改规则后重跑管线；
3. 若是**目标层不一致**：重跑 build_target_db.py → verify_target_db.py → load_target_pg.py；
4. 若是**外部数据**：落盘到 data/external/ 后重跑 release_dates.py 与 field_conflicts.py。

## 五、效率提升的边界（不要过度承诺）

1. 并发不突破站点预算：3 worker 与 1 worker 的总产出都在 60-110 页区间；
2. 采样率仍是 0.86%：所有分布结论只代表样本；
3. PG 在本机不稳定（两次卡恢复）：定位为可重建镜像，权威副本始终是 SQLite；
4. 外部上映数据仍是 0：任务6 只能给条件性上界，不能给 verified 年份。
