# Amazon 电影评论与多源电影信息集成 —— 整体任务分析与阶段规划

> **依据**：`docs/数据存储与管理_ETL作业说明.docx`（下称《说明》）及 `docs/agent.md` 三条前提。
> **定位**：本文档是「分析 + 罗列 + 阶段划分」，用于组织工作，不替代《说明》；凡与《说明》冲突，一律以《说明》为准。

---

## 一、项目本质：交付的是「可追溯的数据集 + 可复现的流程」

《说明》开篇定义了三条验收主线，它们不是三个并列功能，而是同一件事的三个侧面：

| 验收主线 | 含义 | 工程落点 |
|---|---|---|
| **数据正确** | 数量核对、字段完整、约束有效 | 统计核对表、主外键与唯一性、覆盖率 |
| **合并有据** | 实体匹配有定义、有证据、有阈值、有版本 | MergeDecision、规则版本、评价集 |
| **结果可追溯** | 字段级血缘能定位到原始证据 | FieldAssertion、SourceRecord、run_id |

**结论**：本项目交付物 = **数据** + **元数据（血缘与决策）** + **运行记录（批次与日志）** 三件套。
在企业语境中，这正是一份「可信数据资产」的最小构成；只交一张清洗后的宽表，在任何评审里都等同于未交付。

## 二、整体任务分析

### 2.1 数据流全景

```
来源                     原始层(Raw)              暂存层(Staging)           集成层(Integration)        目标层(Mart)
─────────────────────────────────────────────────────────────────────────────────────────────────────────────
movies.txt.gz  ──流式解析──▶ 原始评论行/定位信息 ──▶ 结构化 Review/异常 ──┐
amazon 产品页   ──采集────▶ 页面快照+内容哈希   ──▶ 抽取 Product/字段  ──┼──▶ 电影/人物匹配·补全·冲突 ──▶ Movie / ProductEdition
第三方(IMDb等)  ──接入────▶ 源记录+定位+时间    ──▶ 结构化候选断言     ──┘        │                    ├─▶ Person / MoviePerson
                                                                                    │                    ├─▶ Review / ReviewMapping
        ▲ 每层均保留：源标识(source_id) + 批次标识(batch_id) ◀───────────────────────┘                    └─▶ FieldAssertion / 血缘
```

### 2.3 五类核心难点（决定了阶段划分的先后）

1. **规模与流式**：7,911,684 条评论、253,059 个产品、889,176 个用户，文件约 9.3 GB。禁止整体载入内存，必须按记录边界流式解析，并给出内存/磁盘/时间说明。
2. **异构与半结构**：评论是「键值行」格式，产品页是 HTML，第三方是另一套 schema。三者必须收敛到同一套实体/断言模型。
3. **实体消歧**：作品与人物都需要「候选生成 → 证据打分 → 阈值决策 → 人工复核」四段式，且要防传递闭包误合并。
4. **语义与缺失**：上映日期有「首映 / 地区上映 / 商品发售」三种语义，不能混；只有年份时 `precision=year`；最早评论时间只能作条件性上界。
5. **可追溯与可复现**：字段级血缘要求「候选值 → 处理链 → 最终选择」三跳可重建；同输入同规则版本重跑必须幂等。

### 2.4 必须尽早拍板的关键决策（晚定会导致返工）

| 决策点 | 为什么早定 | 影响面 |
|---|---|---|
| 「同一电影」的操作性定义与例外 | 后续所有 movie_id、评分聚合都依赖它 | 任务4、6、7、8，第十部分 |
| 评论去重键 | 决定逻辑评论数与评分分母 | 任务8、第十部分查询口径 |
| 上映时间语义与精度策略 | 决定字段设计与补全规则 | 任务6、第五部分字段表 |
| 合集/剧集的评论归属与是否计入电影 | 决定 Product–Movie 基数与统计 | 任务3、4、8 |
| ID 生成策略（movie_id/person_id，不用 ASIN） | 决定主键与血缘定位 | 第八部分、第九部分 |
| 原始值/规范值分离的粒度 | 决定 FieldAssertion 结构 | 第五、九部分 |

### 4.1 依赖关系

```
P0 ─▶ P1 ─▶ P2 ─▶ P3 ─┐

                                    P8 ──┘（P8 可与 P5–P7 并行，因它只依赖 P1）
```

- **P1 是硬前置**：没有全量评论就没有 ASIN 清单。

- **P9 必须在 P5–P7 之后**：血缘要记录匹配与选择过程。

## 七、工程实践对照（教学扩展）

| 本作业概念 | 企业对应物 | 常见踩坑 |
|---|---|---|
| source_review_id | 消息 offset / 分区位点 | 用「行号」而不带文件哈希，换文件即撞号 |
| 产品采集状态机 | 采集 SLA / 爬虫平台状态 | 把 200 验证页当成功，指标虚高 |
| Product–Movie 多对多 | 主数据 MDM 的实体关系 | 合集评论复制给每部电影，评分被放大 |
| MergeDecision + 阈值 | 实体解析（record linkage）平台 | 只做标题匹配，传递闭包把 A 和 C 误并 |
| FieldAssertion + FieldSelection | 列级血缘（column-level lineage） | 只存最终值，评审时无法回答「为什么」 |
| ETLRun + 批次 | DataOps / Airflow run metadata | 没有 run_id，出问题无法定位重算范围 |
| 幂等装载 | upsert + 自然键 | 用自增主键导致重跑产生重复实体 |
| 覆盖率与 P/R/F1 | DQ 指标 + 模型评估 | 用开发样本算指标，等于自己考自己 |

## 九、建议推进顺序（单点推进，逐项确认）

1. **Q-1 数据源核验** → 决定 P1 能否启动（是否已压缩、哈希、条数）。
