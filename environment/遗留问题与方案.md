## 二、P1 级（开工前必须确认）

### P1-1　源文件权威性：下载记录与 SHA-256　【开放，可立即执行】

**现状**（已核实元数据，未读取内容）：

| 文件 | 大小 | 备注 |
|---|---|---|
| `movies.txt\movies.txt` | 9,332,887,470 B（8.69 GiB） | 魔数 `70 72 6F 64`="prod"，**纯文本非 gzip** |
| `movies.txt\movies.txt.gz` | 3,321,791,660 B（3.09 GiB） | gzip 尾部 ISIZE=742,952,878，与 txt 长度 mod 2^32 吻合 ✅ |

**为什么必须做**：文档 §任务1 明确要求"记录**下载地址、下载时间、文件大小、SHA-256 校验值和解析程序版本**"。
目前四项里只有"文件大小"有据；且 gzip 的 ISIZE 只校验低 32 位，**不等于 CRC32 通过**，不能作为完整性凭证。

**方案**：

1. 计算 `movies.txt.gz` 的 SHA-256（流式读取 3.09 GB，不解析内容、不注入上下文）。
   ```
   # 用项目 venv Python 流式哈希（内存占用恒定 1 MB 块）
   .venv\Scripts\python.exe -c "import hashlib,sys;h=hashlib.sha256();f=open(r'E:\ETL_Amazon\movies.txt\movies.txt.gz','rb');[h.update(b) for b in iter(lambda:f.read(1<<20),b'')];print(h.hexdigest())"
   ```
2. 生成 `data/source_manifest.json`（可提交，体积小）记录：
   URL、下载时间、字节数、SHA-256、生成方式（gz→txt 的对应关系）、解析程序版本占位。
3. **不要把 txt 的 mtime `2013-03-05` 当作下载时间**——那是 SNAP 打包时间。
   下载时间以 `movies.txt.gz` 的 mtime `2026-10-13 09:07:29` 为准（或由你确认）。
4. 完整性最终仍以文档要求的**记录数核对（7,911,684）**为准，哈希只是第一道闸。

**需你确认**：是否授权我读取该文件用于计算哈希？（只做流式哈希，不解析、不展示内容）

### P1-2　读数据协议（`agent.md` 规则3 的张力）　【待裁决】

**问题**：规则3 禁止加载/解析原始数据源；但任务1 要求"妥善处理空字段、编码异常和文本分隔符"，
任何解析器都必须用真实样本验证才能证明正确。严格执行规则3 则无法验证；擅自读取则违背前提。

**方案（二选一或组合，需你指定）**：

- **A. 仅聚合统计（默认）**：我编写探针脚本，只输出记录数、各字段缺失计数、异常行号清单、长度分布、编码错误计数；**绝不把原文注入上下文**。异常只报"行号 + 异常类型"。
- **B. 一次性白名单抽样**：你授权我抽样 N 条并展示（N 由你定，如 5 条），用于确认字段分隔与编码边界；授权范围与条数可控、可撤销。

### P1-3　任务2 采集合规与 25 万页可行性　【待裁决】

**问题**：文档要求"获取 253,059 个产品页面"，同时要求遵守 robots.txt、请求间隔、并发上限，
且"遇到访问限制不得以绕过验证、登录或封禁作为完成作业的手段"。按 1 req/s 保守限速约需 70 小时；
Amazon 反爬极强，实时全量成功率预计极低。

**有利条款**：文档 §十一 明确"评分**不按实时成功抓取的页面数单独排名**""客观不可访问页面须有证据，
替代数据的范围与完整性须明确""离线快照、第三方补充与实时采集**分别统计**"。

**方案**：

1. 三通道并行且**分开统计分母**：实时采集 / 离线快照 / 第三方数据。
2. 采集器配置：`ROBOTSTXT_OBEY=True`、`DOWNLOAD_DELAY>=2`、`CONCURRENT_REQUESTS=1`、`AUTOTHROTTLE_ENABLED=True`、有限重试。
3. 断点续跑：SQLite 状态表（零安装）+ Scrapy `JOBDIR`。
4. **需你确认**：是否接受"受限/不可访问为主要真实状态"的诚实结果；你手上是否已有离线页面快照。

## 三、P2 级（设计口径，阻塞建模与任务4-6）

### P2-1　上映日期语义与精度模型

**文档依据**：§任务6——"电影首映时间、某地区上映时间与 DVD/Blu-ray 商品发售时间**分别保存**"，
"仅知道年份时保存 `release_year` 和 `precision=year`，**不得人为补成当年 1 月 1 日**"。

**方案**：日期不存单列，存**语义四元组**，从结构上杜绝"不同语义日期参与择优比较"：

| 字段 | 含义 |
|---|---|
| `release_date` | 日期值（可空） |
| `precision` | `exact` / `day` / `month` / `year`（仅年份时日期列留空，不补 1-1） |
| `region` | 地区（NULL=首次公开/全球） |
| `release_type` | `theatrical` / `premiere` / `festival`（作品侧） |

- 商品发售时间**另表** `ProductRelease`（载体/地区/日期），与作品上映严格分表。
- `earliest_review_time` **单独字段**，仅作"条件性上界"；需要推断时另存
  `inferred_release_bound` + 推断条件 + `confidence`，并把 `status` 标记为 `inferred`。
- **硬约束**：`inferred` 值不得覆盖已核实日期（用字段级血缘的"采用规则"保证）。

### P2-2　剧集 / 合集 / 多版本归并层次

**文档依据**：§任务4——合集用 Product↔Movie **多对多**；"合集评论默认仍归属于商品，不能复制给每部电影"；
"剧集与单集如何处理须另行定义，**不得与电影混合计数**"；导演剪辑版/修复版/不同长度版本"须明确归并层次与依据"。

**方案**——显式定义三层归并，并写进规则版本：

| 层 | 含义 | 处理 |
|---|---|---|
| L1 作品 | 同一创作作品（跨 DVD/BD/语言/地区/字幕发行） | 归并为同一 `movie_id` |
| L2 版本 | 同一作品的载体/地区/语言/剪辑版 | 各自 `edition_id`，**不合并** |
| L3 合集 | 一个商品含多部作品 | `ProductMovie` 多对多，`relation_type=boxset_member` |

- **合集**：评论挂 `product_id`，**不复制**到各 `movie_id`；合集内作品仍各自成 `movie_id`。
- **重拍/续集/同名不同作品**：分别建模，不合并（列入"易混淆未合并"案例）。
- **剧集**：独立实体类型（`series` / `season` / `episode`），与电影**分开计数**，报表分列。
- **导演剪辑版/修复版/不同片长**：归入 L2（同作品、不同版本）；若片长差异伴随导演变更或情节不同，视为不同作品，需在规则中给出判据。

### P2-3　评论去重键与评分口径

**文档依据**：§任务8——"声明去重的**目的与键**""相同 ASIN、用户、时间、评分和文本可生成**候选**，
但必须核验记录差异""不同版本上的相似评论不能因文本接近而**无条件删除**""原始记录全部保留"
"Helpfulness 分子不得大于分母，票数不得为负""合并后电影评分须说明是否去重、是否含合集、分母是什么"。

**方案**：

1. **两级标识**：`source_review_id`（原始记录，由文件哈希+记录序号生成，全留）与
   `logical_review_id`（逻辑评论），用 `ReviewMapping` 关联。
2. **候选键**：`(product_id, reviewer_id, review_time, score, md5(review_text))` **只用于生成候选**；
   命中后必须核验字段差异（如 helpfulness、文本末尾差异），差异记录进 `MergeDecision`。
3. **不无条件删除**：跨版本相似评论保留，只在"映射到同一作品 + 同用户 + 同时间"时才视为逻辑重复。
4. **质量规则**：`helpful_votes <= total_votes`、`total_votes >= 0`、`score in 1..5`；违规进 `QualityIssue`。
5. **评分口径**必须三选一并写进报告：是否去重、是否含合集、分母是"评论数"还是"作品数"。

### P2-4　实体合并规则 v1 与评价集构造

**文档依据**：§任务4/5——"先标准化标题…再生成候选匹配""结合上映年份、导演、主演、片长及作品类型验证"
"**单独标题相似、单独年份相同或缺失年份均不足以自动合并**""检查聚类整体一致性，避免 A-B/C-B 导致 A-C 被连带合并"
"至少展示 5 组跨版本合并实例及 5 组易混淆而未合并的实例"；§十要求电影与人物**各 ≥100 对**人工标注样本并报 P/R/F1。

**方案**：

1. **候选生成**（归一化后）：标题规范化（大小写/标点/冠词/罗马数字/别名）→ 阻塞键（`normalized_title` + 年份桶）。
2. **证据验证**（需 ≥2 项一致，且不含"仅标题"或"仅年份"）：年份、导演、主演、片长、外部 ID。
3. **三级判定**：`auto_merge`（证据充分且高置信）/ `needs_review`（部分证据）/ `no_merge`；保存阈值、证据与**规则版本**。
4. **传递一致性**：合并后对聚类做连通性检查；对"链式相似"（A~B、B~C 但 A≁C）**拒绝自动合并**，标注冲突。
5. **评价集**：抽样 ≥100 对（含应合并与不应合并），覆盖同名作品、翻拍、合集、缩写、同名人物等难例；
   **与阈值开发样本分离**，报告 P/R/F1 并说明分母为零时的处理。

**现状**：venv 仅有 `pip/setuptools/wheel/packaging`；无 `requirements.txt`。

**方案**：建立**分层**依赖文件，避免"一把装完"污染环境：

- `requirements/base.txt`：`duckdb`、`pandas`（或 `polars`）、`sqlalchemy`、`psycopg[binary]`（PG 驱动）、`python-dateutil`

- `requirements/match.txt`：`rapidfuzz`、`unidecode`、`pyarrow`

装法与固化：
```
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe -m pip freeze > requirements/lock.txt   # 锁版本，供复现
```
并同步进 `scripts/bootstrap_env.ps1`，使环境可一键重建。

## 五、新暴露的问题（P0 完成后出现）

### N-1　PostgreSQL 常驻依赖 DSH 后台任务　【开放，复现风险】

**问题**：`pg_ctl` 在沙箱不可用；分离/脱离方式会让 startup 进程崩溃；
只有"长生命周期父进程托管"才能正常启动。**会话结束服务即停**，直接影响"端到端可复现"这一提交项。

**方案**：

1. 提供 `scripts/start_all.cmd`：依次确保 **PostgreSQL → PDI → Python venv** 三者可用，
   并打印自检结果（端口/PID/版本）。
2. 文档中明确两种运行模式：
   - **标准模式**（普通机器/验收机）：`pg_ctl start` 或注册为系统服务；
   - **沙箱模式**（本机）：`scripts\pg.cmd serve` 前台运行，由终端窗口或 DSH 后台任务托管。
3. 报告中的"端到端运行步骤"按**标准模式**书写，把沙箱限制作为附注——这样评分方在自己的机器上可正常复现。

### N-2　重装 PDI 会重置 JDBC 驱动　【开放】

**问题**：PDI 自带 `postgresql-42.2.23.jar`；我们为 PG 17 换用 `42.7.14` 并把旧驱动移出 `lib\`。
但 `scripts/setup_pdi.cmd` 重新解压后会**恢复旧驱动**、并**丢掉我们放的驱动**。

**方案**：在 `setup_pdi.ps1` 末尾增加"驱动同步"步骤：

1. 把自带 `lib\postgresql-*.jar` 移出到 `tools/pdi-lib-disabled/`；
2. 从 `tools/downloads/postgresql-42.7.14.jar` 复制到 `lib\`；
3. 校验 `lib\` 中 `postgresql-*.jar` **恰好一个**。
